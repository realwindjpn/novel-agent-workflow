# 结构化主工作台与自由对话浮窗设计

日期：2026-07-30
状态：对话中已确认，等待书面规格复核

## 目标

恢复结构化流水线作为桌面端默认主界面，同时保留自然语言创作能力。用户可以在主窗口快速完成一轮自然语言问答；当用户继续第二轮对话时，系统自动把会话迁移到可拖动、可缩放的自由对话浮窗。自由对话不得破坏主页面的流水线、终端、文件浏览和正式状态。

系统不能依靠提示词让模型“自觉收口”。程序必须维护结构化素材证据、推进状态和明确阈值，并通过两阶段确认把成熟提案交回现有 MCP/core 工作流。

本设计同时恢复模型生成期间的三点动画。

## 已确认的产品决策

- 仅支持桌面端；本次不设计移动端浮窗。
- 主页面默认显示结构化工作台，不再由自由聊天占满中间区域。
- 右下角提供“自由对话”按钮，可直接打开浮窗。
- 主终端接受明确命令，也允许第一次自然语言快速问答。
- 用户提交第二条连续自然语言消息时立即打开浮窗，不等待第二次模型回复。
- 第一轮消息、第一轮回复和第二条用户消息先迁入浮窗，第二次模型回复在浮窗生成。
- 浮窗默认约 `420×560`，可拖动、缩放、最小化。
- 浮窗固定于浏览器视口；主页面滚动时始终可见。
- 浮窗位置和尺寸跨刷新、跨启动持久保存。
- 浮窗提案必须先“提交到主流程”，再在主页面确认“执行”，才能修改正式状态。

## 问题与现状

当前自由创作工作区直接占用主页面，容易让用户误以为结构化流程已经被替代。`creative-chat.js` 可以自然对话、保存会话和编译提案，但存在以下结构性问题：

1. 自由对话与正式工作台争夺同一个主要界面。
2. 当前 `assessReadiness()` 仍依赖一次模型判断；失败被静默处理，程序没有可靠推进。
3. readiness 结果只是一行可忽略的提示，无法阻止无限闲聊。
4. 旧 `chat.js` 的三点生成动画没有接入新的自由创作控制器。
5. 主终端尚未建立明确的“命令或自然语言”分流边界。

## 非目标

- 不改变 core 的状态迁移、门禁、评审或发布规则。
- 不允许浮窗绕过 MCP/core 直接写 `workflow.json` 或章节正式状态。
- 不实现移动端、跨设备同步或多人协作。
- 不使用模型判断一段输入是否可以作为命令执行。
- 不在本次增加流式 token 渲染；生成动画表示完整响应仍在等待。
- 不删除 CLI、终端、流水线、文件抽屉或现有正式执行卡。

## 总体架构

```text
结构化主工作台
流水线 / 终端 / 文件 / 正式状态 / 执行确认
        ▲
        │ 已验证提案 + 第一次确认
        │
自由对话浮窗
对话 / 试写 / 素材账本 / 提案预览
        ▲
        │ 第二条连续自然语言消息或手动打开
        │
主窗口快速问答
第一轮用户消息 + 第一轮模型回复
```

职责边界：

- 模型负责生成自然语言、抽取候选素材和编译提案。
- 程序负责输入分流、会话迁移、素材证据校验、阈值推进、浮窗状态和两阶段确认。
- MCP/core 继续负责所有正式写入和状态机约束。

## 组件边界

### 新增 `web/conversation-router.js`

负责主终端输入分类和连续对话计数。它只依赖确定性解析规则，不调用模型判断输入类型。

公开接口建议为：

```js
classify(text) -> { kind: "command" | "natural", command? }
recordQuickRound(sessionId, userTurnId, assistantTurnId)
shouldPromote(nextText, now) -> boolean
resetQuickSequence(reason)
```

### 新增 `web/floating-chat.js`

只负责浮窗 UI 和几何状态：创建、显示、拖动、缩放、最小化、恢复、视口限制、busy 动画和主窗口记录迁移。它不理解模型提示词、提案 schema 或正式命令。

### 调整 `web/creative-chat.js`

继续作为自由创作状态机。新增明确的 view 生命周期：

```js
beginOperation({ kind, surface })
endOperation({ kind, outcome })
renderCoverage(ledger)
renderGuidedMode(missingFields)
markProposalStale(reason)
```

控制器负责对话、素材账本、提案状态和持久化，但不负责窗口拖动或终端解析。

### 调整 `web/chat.js`

保留主窗口的快速问答卡和正式计划卡。第一轮自然问答使用带 `data-quick-session` 的临时节点；正式计划卡仍是第二阶段执行闸门。

### 调整 `web/app.js`

负责启动时组合 router、floating window、creative controller 和当前活动书籍；主页面默认进入结构化模式。

### 保持 `web/creative.js` 与 `web/llm.js`

- `creative.js` 继续负责本地、浏览器和内存持久化。
- `llm.js` 继续分离自然回复、素材抽取/readiness 和结构化编译器调用。
- API key 不进入会话、素材账本、提案或备份。

## 主窗口输入分流

命令分流必须使用白名单和现有解析器：

- 以 `novel-workflow` 开头的输入始终按命令处理；即使参数错误，也显示命令错误，不转成自然语言。
- `help`、`ls`、`cat`、`tree`、`clear`、`reset` 等现有辅助命令按命令处理。
- 能被现有结构化命令解析器完整识别的输入按命令处理。
- 其他输入按自然语言处理。

不能让模型决定命令是否可执行，避免自然语言被误转换成 CLI，或错误命令绕过终端错误处理。

执行明确命令会结束当前主窗口连续对话计数，但不会删除已经持久化的自然对话记录。

## 第一轮快速问答

第一次自然语言输入在主窗口中显示为轻量快速问答卡：

1. 渲染用户气泡。
2. 立即渲染三点生成动画。
3. 调用自由创作回复模型。
4. 成功后用模型回复替换动画。
5. 回复下方显示“继续追问将转入自由对话窗”。

快速问答卡位于主终端区域内，但与真实终端输出使用不同 DOM 类型和样式；它不能改变终端历史、流水线步骤或文件状态。

第一轮用户消息和模型回复立即写入活动书籍的 creative session，并记录稳定 turn id。主窗口卡片是临时视图，不是唯一数据副本。

如果页面刷新，主窗口不自动恢复快速问答卡，以保证结构化工作台干净；完整记录仍可从自由对话浮窗恢复。

## 第二轮迁移事务

“连续第二轮”的精确定义是：在第一轮回复成功后的 15 分钟内，用户再次提交自然语言，并且期间没有执行正式命令、切换书籍或明确结束对话。

第二条自然语言提交时：

1. 创建或恢复浮窗。
2. 从 creative session 读取第一轮稳定 turn id。
3. 在浮窗依次渲染第一轮用户消息、第一轮模型回复和第二条用户消息。
4. 确认三个节点渲染成功后，再删除主窗口快速问答卡。
5. 在浮窗渲染三点动画并请求第二次模型回复。

迁移失败时，主窗口快速问答卡保持原样，第二条用户消息保留在未发送缓冲中，并显示可重试错误。迁移不得复制持久化 turn，也不得把同一消息追加两次。

手动点击“自由对话”按钮会直接打开浮窗，不要求先完成快速问答。浮窗最小化期间输入自然语言时，浮窗自动恢复。

## 浮窗交互

### 几何规则

- 默认尺寸：`420×560`。
- 最小尺寸：`340×360`。
- 最大尺寸：宽度不超过视口的 80%，高度不超过视口的 85%。
- 浮窗与视口边缘至少保留 12px。
- 标题栏负责拖动，右下角负责缩放。
- 浏览器尺寸改变后，程序把浮窗位置和尺寸限制回可见范围。
- 主页面滚动不会改变浮窗的屏幕坐标。

位置、尺寸和最小化前状态使用独立的浏览器本地设置保存，不写入书籍 creative session。窗口几何在不同书籍间共用；对话内容按活动书籍隔离。

### 最小化与关闭

- 最小化后显示右下角圆形“对话”按钮。
- 有未读回复、正在生成或待处理提案时显示状态标记。
- 恢复后回到最小化前的位置和尺寸。
- 关闭动作只隐藏浮窗，不删除会话。
- 切换书籍时浮窗清空当前视图，再载入新书会话，不能混合两本书的记录。

## 生成动画生命周期

三点动画必须成为 view 生命周期的一部分，而不是散落在某条旧 LLM 路径中。

需要覆盖：

- 主窗口第一轮自然回复。
- 浮窗后续自然回复。
- “你来决定”。
- 自动或手动编译提案。
- 提案重新编译。

规则：

- 请求开始后立即显示。
- 同一操作最多存在一个动画节点。
- 操作期间暂时阻止重复提交。
- 成功、provider 错误、网络错误、超时、窗口关闭和书籍切换都会清理动画与 busy 状态。
- 历史恢复和会话迁移不播放动画。
- `prefers-reduced-motion` 下保留静态三点状态，不执行跳动动画。

## 程序化结构收口

### 状态机

```text
exploring
  -> collecting
  -> guided
  -> proposal-ready
  -> proposal
  -> handed-off
```

- `exploring`：自由发散，尚无足够结构证据。
- `collecting`：已经抽取到部分有效素材。
- `guided`：达到程序阈值仍有缺项，程序开始逐项引导。
- `proposal-ready`：满足正式提案最低证据条件。
- `proposal`：已经生成提案卡，允许讨论、重编译或提交。
- `handed-off`：用户已把提案交给主流程，等待主页面第二次执行确认。

### 素材证据账本

每本书维护以下字段：

1. 核心创意 `premise`
2. 主角与欲望 `protagonist`
3. 中央冲突 `central_conflict`
4. 风险与代价 `stakes`
5. 世界规则 `world`
6. 风格与目标读者 `style_audience`
7. 结局倾向 `ending_direction`

每项包含：

```json
{
  "value": "自然语言内容",
  "source_turn_ids": ["turn-id"],
  "status": "candidate|confirmed|assumed|conflicted",
  "updated_at": "ISO-8601"
}
```

素材抽取是独立的结构化模型调用，但程序负责硬校验：

- `source_turn_ids` 必须存在于当前书籍会话。
- 引用 turn 必须包含支持该值的实际文本。
- 空字符串、未知 turn、重复 id 和不支持的状态被拒绝。
- 新值与已确认值冲突时标记 `conflicted`，不能覆盖 confirmed 值。
- 模型只说“已经成熟”不会改变状态。

### 有效回合

程序同时记录“已完成回合”和“有效回合”。已完成回合是成功得到自然语言回复的用户/模型消息对，用于保证对话不会无限持续；有效回合用于衡量结构素材是否真的有进展。

一个用户回合只有在满足以下任一条件时才计为有效：

- 素材抽取新增或实质修改至少一项有效证据。
- 用户明确确认、否定或修正账本中的一项内容。

纯粹的“好”“继续”“可以”等回复不会增加有效回合数，但仍保存在完整对话中。

### 推进阈值

- 自动提案：核心创意、主角、冲突、代价、风格五项有效，并且累计至少 3 个有效用户回合。
- 引导模式：累计 6 个已完成回合，或累计 4 个有效回合，仍未达到自动提案条件时触发；以先到者为准。
- 结构化草案：累计 10 个已完成回合后仍有缺项时强制触发，不受有效回合数影响。程序自动生成带缺项、假设和不确定性的草案。

引导模式由程序选择缺失字段，并要求模型围绕一个缺项提问；不是只在提示词中说“请收口”。

10 回合草案不等于正式可提交提案：

- 未获得用户自主授权时，缺失必填项保持 unresolved，“提交到主流程”按钮禁用。
- 用户明确点击“你来决定”或“由模型补齐缺项”后，模型可以生成 `assumed` 值；所有 assumed 值必须在提案卡中可见。
- 只有必填字段通过程序校验后，才能提交到主流程。

用户可随时手动点击“编译方案”。手动编译跳过回合数要求，但不能跳过字段校验。

## 提案更新与失效

提案记录生成时使用的 source turn ids 和素材账本版本。提案生成后，如果用户修改以下任一内容，提案变为 stale：

- 核心创意
- 主角
- 中央冲突
- 风险与代价
- 已确认禁区

stale 提案不能提交到主流程。浮窗显示“内容已变化，需要重新编译”，并提供重新编译按钮。旧提案保留历史状态，不被静默覆盖。

## 两阶段正式交接

第一阶段在浮窗：

- 显示提案摘要、素材覆盖、模型假设、不确定性和来源范围。
- 用户点击“提交到主流程”。
- 程序再次验证提案未 stale、必填项完整、来源 turn 有效。

通过后：

1. 主页面定位到对应结构化阶段。
2. 主页面显示现有正式 plan card。
3. 浮窗自动最小化，但会话和提案保留。
4. 正式状态尚未改变。

第二阶段在主页面：

- 用户点击“执行”。
- 现有 NWLocal/MCP/core 边界执行真实命令。
- core 再次验证 15 字段 intake 和状态机条件。
- 成功后提案标记 committed；失败时保留 proposal 状态以便修正和重试。

任何单一模型输出、readiness 结果或浮窗按钮都不能直接修改正式状态。

## 错误处理

### 自然回复失败

- 清理动画和 busy 状态。
- 保留用户消息并显示 provider/network/timeout 等具体错误。
- 不调用规则引擎，不执行正式命令。
- 允许原消息重试。

### 素材抽取失败

- 自然语言回复仍然保留。
- 本轮账本不更新，下轮重试。
- 连续两次失败后显示可展开的手动素材清单。
- 抽取失败不伪造“未准备好”，也不清除已有证据。

### 编译失败

- 对话、账本和旧提案全部保留。
- 显示 parse/schema/provider 的具体错误和重试入口。
- 不创建正式计划卡。

### 主流程执行失败

- 主页面显示 core 的真实拒绝原因。
- 浮窗提案保持可修改状态。
- 不把失败写成 committed。

### 迁移、窗口和书籍切换失败

- 迁移完成前不删除主窗口快速问答。
- 书籍切换取消当前 UI 请求、清理动画，再装载新会话。
- 浮窗几何数据损坏时回到默认右下角，而不是阻止应用启动。

## 持久化

书籍 creative session 增加版本化的结构状态：

```json
{
  "conversation_state": {
    "phase": "collecting",
    "completed_rounds": 5,
    "effective_rounds": 3,
    "coverage_version": 4,
    "coverage": {},
    "active_proposal_id": null
  }
}
```

迁移需向后兼容：旧会话没有 `conversation_state` 时使用空账本和 `exploring`，不修改旧 turns、drafts 或 proposals。

浮窗几何单独保存在浏览器本地设置中，不进入 ZIP 创作备份。对话、账本和提案继续进入本地 creative store 和 ZIP 备份。

## 可访问性与桌面限制

- 标题栏、最小化、恢复、关闭和缩放手柄具备可读名称。
- 拖动和缩放后保持输入框、发送按钮和提案动作可见。
- 键盘可以聚焦浮窗、最小化按钮和消息输入。
- 生成状态通过 `aria-live` 告知，但不会反复朗读动画点。
- 本次不保证窄于 900px 的布局品质；视口过小时仍限制几何，确保浮窗可关闭。

## 测试设计

### 单元测试

- 确定性命令白名单不会把自然语言作为命令执行。
- `novel-workflow` 错误命令不会回退成自然聊天。
- 第一轮自然语言留在主窗口并持久化稳定 turn id。
- 第二条连续自然语言在请求前触发浮窗迁移。
- 迁移不会复制 turn；失败不会删除主窗口记录。
- 命令、超时、书籍切换和显式结束会重置连续计数。
- 浮窗位置、尺寸、最小化和视口限制可恢复。
- 动画在成功、失败、超时、关闭和书籍切换后清理。
- 素材账本拒绝未知 source id、冲突覆盖和空字段。
- 自动提案、6 回合引导和 10 回合强制草案阈值由程序状态触发。
- stale 提案不能提交。
- 未经两阶段确认，executor 调用次数为零。

### 静态与安全测试

- 主页面默认结构化模式。
- public 端不能访问本地 creative session 或正式执行 API。
- API key 不进入 creative store、ZIP 或 UI 日志。
- 浮窗文本和模型内容继续转义后渲染。

### 真实浏览器验收

1. 启动本地应用，确认主页面显示结构化工作台。
2. 输入一条自然语言，观察主窗口用户气泡、三点动画和回复。
3. 输入第二条自然语言，确认浮窗立即打开、三条现有记录迁移、第二次动画和回复出现在浮窗。
4. 确认主页面快速问答消失，流水线和终端仍完整。
5. 拖动、缩放、最小化、恢复并刷新，确认几何恢复。
6. 滚动主页面，确认浮窗保持屏幕位置。
7. 输入明确 CLI，确认不打开浮窗并正常执行或显示命令错误。
8. 构造 6 个已完成回合和 10 个已完成回合场景，确认程序进入引导和强制草案阶段。
9. 修改关键事实，确认提案 stale 且不能提交。
10. 提交提案到主流程，确认主页面出现正式计划卡但状态未改变。
11. 第二次点击执行后，确认只有 MCP/core 成功才改变正式状态。
12. 模拟 provider、抽取、编译和执行失败，确认消息不丢失且动画不残留。

## 验收标准

1. 结构化流水线是桌面端默认主界面。
2. 主窗口允许且只承载一次连续自然语言快速回复。
3. 第二条连续自然语言提交时自动迁移到浮窗，第二次回复不在主窗口生成。
4. 浮窗约 `420×560`，可拖动、缩放、最小化，并跨重启恢复几何。
5. 主页面滚动时浮窗始终可见。
6. 三点动画覆盖所有模型生成路径，并在所有终止路径清理。
7. 程序通过素材证据、完成回合数和有效回合数推进，不依赖模型自报 readiness。
8. 10 回合后不会无限闲聊，而会产生明确结构化草案和缺项状态。
9. 关键事实变化会使旧提案 stale。
10. 浮窗提案和主页面执行卡构成两个独立确认闸门。
11. 未经最终执行确认，正式 core 状态不改变。
12. 旧 creative session 无需人工迁移即可继续使用。
