# novel-workflow web live runner (browser SPA)

A zero-build, zero-backend, zero-network-of-its-own web UI that drives the
`novel-agent-workflow` package **in the browser** via [Pyodide](https://pyodide.org/)
(loaded from jsDelivr at runtime). It is the third entry point into the same
state machine that the CLI and the MCP server expose — it is not a separate
product.

The runner lives in this repo at `web/`. The rest of the project (`src/`,
`tests/`, `docs/MCP.md`, …) is unaware of it; the contract is one-way: the
web side snapshots the Python package, never the other way around.

## Three faces of the same state machine

| Surface | Where | Talks to | Code sharing |
|---|---|---|---|
| CLI | `novel-workflow` console entry point | `src/novel_workflow/*.py` directly | — |
| MCP | `novel-workflow mcp` stdio server | `src/novel_workflow/*.py` directly | — |
| **Web** | `web/index.html` opened in a browser | Pyodide running the snapshot in `web/sources.js` | snapshot only |

The web runner does **not** import from the CLI or the MCP server, and they
do not import from it. The three code paths are independent. What they
share is the **core source contract** — every surface loads the same Python
package. For the web side, that means `web/sources.js` is a verbatim snapshot
of the files under `src/novel_workflow/`, generated by:

```bash
python scripts/gen_web_sources.py
```

So the browser executes the *same* `core.py`, the *same* state machine, the
*same* gate enforcement that the CLI and the MCP server do. Change the
Python package, regenerate the snapshot, and all three surfaces move
together. Limits (`workflow.json["limits"]`) and the workflow file format
are the same on every surface — there is no second copy.

The runner ships no bundled environment, no API keys, no telemetry. Pyodide
fetches its own interpreter and packages from jsDelivr on first load
(~10s; cached after that). The only state the browser touches lives in
Pyodide's in-memory filesystem plus the user's `localStorage` for the
optional LLM settings (see below).

## Files (~600 KB total, all client-side)

| File | Role |
|---|---|
| `index.html` | single-page app shell, loads Pyodide from jsDelivr |
| `app.js` | Pyodide bridge (NWB: read state, run command, refresh files) |
| `chat.js` | plain-Chinese (白话) intent engine + LLM BYOK dispatch |
| `llm.js` | OpenAI-compatible BYOK client (settings in `localStorage`) |
| `sources.js` | snapshot of `src/novel_workflow/*.py` — **generated, do not edit** |
| `tape.js` | recorded demo session used by Replay mode |
| `ansi.js` | ANSI → HTML colorizer for terminal output |
| `explorer.js` | file tree rendering |
| `guide.js` | guided walkthrough of the 22-step pipeline |

## Modes

- **Code** — the original 22-step state-machine walkthrough, terminal, and
  file tree. Live mode actually runs `core.py` + `cli.py` inside Pyodide;
  Replay mode plays back `tape.js` for demos when the WASM engine is
  unavailable.
- **Plain Chinese (白话)** — natural-language intent layer that maps to the
  same commands. Write actions go through a confirm-before-execute card so
  the state-machine gates stay authoritative.
- **LLM BYOK (opt-in)** — bring-your-own-key against any OpenAI-compatible
  endpoint. The key never leaves the browser (stored in `localStorage`).
  When the key is absent, unreachable, or returns an error, the runner
  silently falls back to the rule-based intent engine.

## Local preview

The folder is fully static; any HTTP server works:

```bash
cd web
python3 -m http.server 8080
# open http://localhost:8080
```

Pyodide fetches Python and packages from jsDelivr on first load (~10s).
Subsequent loads are cached. If the WASM engine takes more than ~150s to
respond, the page falls back to Replay mode automatically so you can still
explore the 22-step flow.

## Refreshing the source snapshot

After any change to `src/novel_workflow/`, regenerate the browser's view
of the package:

```bash
python scripts/gen_web_sources.py
```

The script writes `web/sources.js` from a fixed, ordered list of package
files. Hand-edits to `web/sources.js` are silently overwritten on the next
run; do not commit them. The list of files lives at the top of
`scripts/gen_web_sources.py` and is the canonical reference for what the
web runner mounts.

The committed `web/sources.js` always matches the Python sources at the
same commit (modulo whitespace). The Python sources are the source of
truth; the snapshot is a derived artifact.

## Versioning

The package version in `web/package.json` is kept in lockstep with the
Python package's `__version__`. The Miaoda-built deployment of this
runner lives outside the repo (it is rebuilt from this folder whenever
`sprint/default` advances) — the URL is not stored here so this folder
stays a portable, self-contained bundle.
